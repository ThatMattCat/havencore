# Tool Development Guide

This guide covers creating tools and integrations for HavenCore. Every agent tool is an MCP (Model Context Protocol) server — there is no in-process "legacy" tool registry.

## Overview

All of the agent's tools are provided by MCP servers: modules hosted by the `mcp-tools` service over MCP Streamable HTTP (each module still runs standalone over stdio for testing) and wired into the LLM's function-calling interface via the `UnifiedTool` abstraction. To add a tool, add (or copy) an in-tree MCP module — see [Adding an MCP tool to HavenCore (in-tree)](#adding-an-mcp-tool-to-havencore-in-tree) below.

## Adding an MCP tool to HavenCore (in-tree)

The fastest path to a new tool is to copy one of the existing in-tree MCP
modules under `services/agent/selene_agent/modules/` and register it in
`.env` plus the `mcp-tools` host app's module registry
(`selene_agent/mcp_http_app.py`). The mcp-tools service mounts the module at
`/mcp/<name>` and the agent discovers its tools over Streamable HTTP at
startup — no agent code changes needed.

Every in-tree module has the same three-file layout. The server file is named `mcp_server.py` by convention in the template modules, but it can have any name as long as `__main__.py` imports its `main()` — several in-tree modules use a different name (e.g. `face_mcp_server.py`, `github_mcp_server.py`, `qdrant_mcp_server.py`, `server.py`):

```
services/agent/selene_agent/modules/mcp_<your_tool>/
├── __init__.py          # empty is fine
├── __main__.py          # entry point — runs mcp_server.main()
└── mcp_server.py        # the server: tool list + handler
```

### 1. Scaffold the module

```bash
cd services/agent/selene_agent/modules
cp -r mcp_general_tools mcp_hello          # pick any existing module as your template
# prune the template's tools so you start empty
```

`__main__.py` is boilerplate — keep it identical:

```python
if __name__ == "__main__":
    from .mcp_server import main  # Import here to avoid circular imports
    main()  # MCPServer.run("stdio") is synchronous (it owns the event loop)
```

### 2. Define your tools in `mcp_server.py`

Minimal working server — one tool, no external deps. Tools are typed
functions registered on an `MCPServer` (the mcp SDK 2.x decorator API);
each tool's `inputSchema` is generated by pydantic from the function
signature:

```python
from typing import Annotated, Literal

from pydantic import Field

from mcp.server import MCPServer

from selene_agent.modules._mcp_params import NULL_OK


class HelloServer:
    def __init__(self):
        self.mcp = self._build_mcp()

    def _build_mcp(self) -> MCPServer:
        mcp = MCPServer("havencore-hello", version="0.1.0")

        @mcp.tool(
            name="say_hello",
            description="Greets the user by name.",
            structured_output=False,
        )
        async def say_hello(
            name: Annotated[str, Field(description="Name to greet")],
            style: Annotated[Literal["plain", "shouty"], NULL_OK, Field(
                description="Optional greeting style."
            )] = None,
        ) -> str:
            if style == "shouty":
                return f"HELLO, {name.upper()}!"
            return f"Hello, {name}!"

        return mcp


def main():
    """Stdio entry point (`python -m selene_agent.modules.mcp_hello`)."""
    HelloServer().mcp.run("stdio")
```

The agent reads the returned text back out and hands it to the LLM as the
tool result. Return an error message the same way — the orchestrator will
show it in the dashboard's tool-call card.

Conventions every in-tree module follows:

- **Explicit `name=` / `description=` kwargs on `@mcp.tool`** — never
  rely on the function name / docstring pickup.
- **`structured_output=False` on every tool**, so results stay a single
  `TextContent` string (no `outputSchema` in `tools/list`, no
  `structuredContent`) — the wire shape the agent expects.
- **`Annotated[..., Field(description=...)]` on every parameter.** The
  descriptions become the LLM-visible argument docs.
- **Optional parameters are `Annotated[T, NULL_OK, Field(...)] = None`**
  — bare type, `None` default, plus the `NULL_OK` marker from
  `selene_agent/modules/_mcp_params.py`. This keeps the generated
  property the plain `{"type": ...}` shape (no `anyOf [T, null]` union)
  while still accepting the explicit JSON `null` that LLMs routinely
  send for parameters they mean to omit.
- **`Literal[...]` for enum-shaped parameters** — generates a JSON
  Schema `enum`.
- **Conditional registration for env-gated tools**: wrap the decorated
  function in `if <CREDENTIAL>:` so a tool whose credential is unset is
  never registered (see `wolfram_alpha` / `send_signal_message` in
  `mcp_general_tools`).

### 3. Register the server

Three places:

1. **A bearer token in `.env`.** The `mcp-tools` host refuses to serve a
   module unauthenticated — a missing token var means the module is not
   mounted at all:

   ```bash
   MCP_TOKEN_HELLO="$(openssl rand -hex 24)"
   ```

2. **A loader + `MODULES` entry in `selene_agent/mcp_http_app.py`**, so
   the `mcp-tools` service mounts the module at `/mcp/hello`:

   ```python
   async def _load_hello() -> LoadedModule:
       from selene_agent.modules.mcp_hello.mcp_server import HelloServer
       inst = await asyncio.to_thread(HelloServer)  # keep blocking init off the loop
       return LoadedModule("hello", inst, mcp=inst.mcp)

   MODULES = [
       # ...
       ("hello", "MCP_TOKEN_HELLO", _load_hello),
   ]
   ```

3. **An `MCP_SERVERS` entry in `.env`**, so the agent connects to the
   mount. The `name` must match the mount name registered in `MODULES`:

   ```json
   {
     "name": "hello",
     "url": "http://mcp-tools:6010/mcp/hello",
     "token_env": "MCP_TOKEN_HELLO",
     "enabled": true
   }
   ```

   The retired stdio shape (`{"name", "command", "args"}`) is rejected
   with a config error — the agent's MCP client is HTTP-only.

### 4. Restart and smoke-test

```bash
# .env changed, so recreate both services (a bare restart won't re-read env)
docker compose down mcp-tools agent && docker compose up -d mcp-tools agent

# Did mcp-tools mount it?
curl "http://${HOST_IP_ADDRESS}:6010/health" | jq '.mounted, .failed'

# Did the agent connect and discover its tools?
curl http://localhost:6002/api/mcp/status | jq '.connected_servers, .tools_by_server'
```

When iterating on an **already-registered** module, code-only changes are
cheaper: the module source is bind-mounted into `mcp-tools`
(`./services/agent/:/app`), so

```bash
docker compose restart mcp-tools
```

picks them up. The agent's sessions to the restarted host heal lazily —
the first tool call fails, a background reconnect kicks in, and a retry
succeeds — or `docker compose restart agent` reconnects (and re-reads
tool schemas) immediately. Dependency changes (`pyproject.toml`) still
need the image rebuild cycle: `docker compose down mcp-tools agent &&
docker compose build agent && docker compose up -d` (the `mcp-tools`
service reuses the agent image).

Then run the stdio or HTTP handshake from the **MCP server testing**
section below to exercise your new tool without going through the LLM.

### Tips

- **Read the mcp-tools logs.** Tool modules run inside the `mcp-tools`
  service; write diagnostics with a logger rather than `print()` so they
  land in `docker compose logs mcp-tools`.
- **Wrap external calls in timeouts.** The orchestrator already caps
  `call_tool()` at `MCP_TOOL_TIMEOUT_SECONDS` (default 120s), but a tool
  that blocks on a hung socket burns that entire window.
- **A dropped connection heals itself.** Transport-level failures (broken
  or closed stream, HTTP connect/read errors, a "session terminated /
  session not found" answer after an `mcp-tools` restart) mark the
  agent's connection dead and trigger a bounded background reconnect —
  `MCP_RECONNECT_MAX_ATTEMPTS` (default 3) tries with exponential backoff
  seeded by `MCP_RECONNECT_BACKOFF_SECONDS` (default 2s); after an
  abandoned cycle, a later tool call re-arms one fresh cycle once
  `MCP_RECONNECT_REARM_COOLDOWN_SECONDS` (default 60s) has elapsed.
  Calls made while the server is down fail fast instead of waiting out the
  tool timeout. An ordinary tool error (a raised exception, or a result with
  `isError`) is *not* treated as a dead transport, so one failing tool never
  takes its sibling tools offline.
- **Return actionable errors.** The LLM recovers well from
  `"Error: city 'Foo' not found — try one of: [Rome, Foothill, ...]"`
  and poorly from `"Error: 404"`.

## External MCP servers

The agent's MCP client is plain Streamable HTTP: an `MCP_SERVERS` entry
can point at any server that speaks MCP Streamable HTTP, not just the
in-tree `mcp-tools` mounts.

```json
{
  "name": "my-external-server",
  "url": "http://192.168.1.50:8123/mcp",
  "token_env": "MCP_TOKEN_MY_EXTERNAL",
  "enabled": true
}
```

`token_env` is optional — omit it for an endpoint that doesn't require a
bearer token. There is no stdio client anymore: a server that only
speaks stdio has to be fronted by a Streamable HTTP transport before the
agent can use it.

Conversely, the `mcp-tools` mounts are consumable by any external MCP
client (custom connectors, IDE integrations): configure the client with
`http://<host>/mcp/<name>` (through the nginx gateway) or
`http://<HOST_IP_ADDRESS>:6010/mcp/<name>` (direct) plus the module's
bearer token. See the
[mcp-tools service doc](../../mcp-tools/README.md) and the
[API reference](../../../api-reference.md#mcp-tool-mounts-streamable-http).

## Tool Registry Management

### Registered tools

Every agent tool is an MCP tool. List the current registry, grouped by MCP server, over HTTP:

```bash
# List all registered tools
curl http://localhost:6002/api/tools

# Response:
{
  "tools_by_server": {
    "homeassistant": [
      {
        "name": "ha_get_domain_entity_states",
        "description": "Get states for all entities in a domain",
        "parameters": {}
      }
    ],
    "general_tools": [
      {
        "name": "brave_search",
        "description": "Search the web with Brave",
        "parameters": {}
      }
    ]
  },
  "total": 69
}
```

Because there is no legacy tool source, there is no name-conflict resolution: tool names simply have to be unique across servers.

### Reloading MCP servers (requires restart)

MCP servers are loaded once from `MCP_SERVERS` at agent startup — adding
or removing a server means editing the JSON array in `.env` and
recreating both `mcp-tools` and the agent:

```bash
docker compose down mcp-tools agent && docker compose up -d mcp-tools agent
```

Code changes inside an already-registered module are cheaper — see
"Restart and smoke-test" above (`docker compose restart mcp-tools`, agent
heals lazily).

## Testing and Debugging Tools

### Unit tests

The agent's Python test suite lives in `services/agent/tests/` (pytest + pytest-asyncio, `asyncio_mode=auto`). Run it inside the agent container so imports and env resolve. The image is built without dev deps, so install pytest first:

```bash
docker compose exec -T agent pip install -q pytest pytest-asyncio
docker compose exec -T -w /app agent python -m pytest
```

### MCP Server Testing (stdio)

In production the modules are served over Streamable HTTP by `mcp-tools`,
but every module keeps a stdio entry point for manual testing:
`python -m selene_agent.modules.<name>` runs the same `MCPServer` over
JSON-RPC on stdio. Run it inside the **agent container** (or
`mcp-tools` — same image) — that's where the Python deps, the loaded
`.env`, and `shared_config` live.

Requires the agent container to be running (`docker compose up -d agent`).

#### Quick sanity check — does the server start and list tools?

Run the full MCP handshake (`initialize` → `notifications/initialized` → `tools/list`)
against the server:

```bash
docker compose exec -T agent python -m selene_agent.modules.mcp_homeassistant_tools <<'EOF'
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual-test","version":"0.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
EOF
```

Expect two JSON-RPC responses on stdout: the `initialize` result (protocol
version + server info) and the `tools/list` result (array of tool definitions
with `name`, `description`, `inputSchema`). Server logs go to stderr —
`docker compose exec` interleaves both, so pipe to `grep -E '^\{'` if you only
want the JSON.

Swap the module for any of the others:

| homeassistant | `selene_agent.modules.mcp_homeassistant_tools` |

| music_assistant | `selene_agent.modules.mcp_music_assistant_tools` |

#### Exercising a specific tool

Add a `tools/call` message with the tool name and arguments. Important: if the
tool makes an external call (HA REST/WS, web API, vector DB), stdin EOF from a
heredoc can race the response and kill the subprocess mid-reply. Wrap the
input so stdin stays open until the tool finishes:

```bash
(cat <<'EOF'
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual-test","version":"0.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"ha_list_services","arguments":{"domain":"light"}}}
EOF
sleep 3) | docker compose exec -T agent python -m selene_agent.modules.mcp_homeassistant_tools 2>&1 | grep -E '^\{'
```

The response wraps the tool's output in `result.content` (an array of
`{type, text}` blocks). `isError: false` means the transport succeeded — a
tool reporting its own failure will still come back with `isError: false` and
the error text inside `content`. Bump `sleep` higher for slow tools.

### MCP Server Testing (Streamable HTTP)

To exercise a mounted module the way the agent reaches it, POST JSON-RPC
to its `/mcp/<name>` mount with the bearer token. Streamable HTTP
requires an `Accept` header offering both JSON and SSE; the response body
arrives as an SSE event, and the `initialize` response carries an
`Mcp-Session-Id` header that must be echoed on subsequent requests of the
same session:

```bash
curl -is "http://${HOST_IP_ADDRESS}:6010/mcp/reminder" \
  -H "Authorization: Bearer $MCP_TOKEN_REMINDER" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual-test","version":"0.0"}}}'
```

A wrong or missing token gets `401`. A `421` means the Host header
failed the DNS-rebinding allowlist — add the name you're using to
`MCP_HTTP_ALLOWED_HOSTS`. A `403` "Invalid Origin header" means the
Origin failed it (browser-extension clients like Island's connector) —
add the full origin to `MCP_HTTP_ALLOWED_ORIGINS`.

For a full sweep with a real MCP client session,
`tests/tools_snapshot.py --http` connects to every mount configured in
`MCP_SERVERS` and snapshots each module's `tools/list`:

```bash
docker compose exec -T agent python /app/tests/tools_snapshot.py --http /tmp/snap
```

#### Schema parity fixtures

Baseline tool schemas live in
`services/agent/tests/fixtures/tool_schemas/<module>.tools.json` (name,
description, `inputSchema` per tool, sorted keys), and per-module pytest
parity tests compare the live decorator-generated surface against them.
`tests/tools_snapshot.py` regenerates the fixtures (stdio by default,
`--http` for the mounted servers — both produce the same shape). After
any intentional schema change, re-run it, diff, and commit the updated
fixture alongside the code.

#### End-to-end via the chat API

To test a tool the way the LLM actually invokes it — including tool
selection, argument synthesis, and the follow-up response — POST a prompt
that forces the tool to `/v1/chat/completions` and inspect the tool-call
handling in the response.

### Debugging Tools

```python
# Add debugging to tools
import logging

logger = logging.getLogger(__name__)

def debug_tool_wrapper(func):
    """Decorator to add debugging to tools."""
    def wrapper(*args, **kwargs):
        logger.debug(f"Tool {func.__name__} called with args: {args}, kwargs: {kwargs}")
        
        try:
            result = func(*args, **kwargs)
            logger.debug(f"Tool {func.__name__} result: {result}")
            return result
        except Exception as e:
            logger.error(f"Tool {func.__name__} error: {e}")
            raise
    
    return wrapper

@debug_tool_wrapper
def my_custom_tool(param: str) -> Dict[str, Any]:
    # Tool implementation
    return {"result": param, "success": True}
```
